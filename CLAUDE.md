# CLAUDE.md

Self-hosted personal finance app. Repo dir is `finance`, but the root package is `argent` and workspace packages are `@argent/*`.

## Stack
- Bun workspaces monorepo: `packages/shared` (`@argent/shared`: types + zod request schemas, also used by the frontend for validation), `packages/backend` (Hono + Drizzle + Postgres), `packages/frontend` (Vue 3 + Vite + Tailwind + vue-router + TanStack Query for Vue + oidc-client-ts).
- Auth: Authentik OIDC. The SPA runs the auth code flow; the backend validates the Bearer JWT via JWKS (`jose`).
- Deploy: container images in `docker/` (built on SUSE BCI `bci-micro:15.7`: Bun runtime for the API, nginx for the SPA; non-root user 65532, read-only root file system, no shell tools beyond bash) and the Helm chart `charts/argent` (replaces the old `k8s/` manifests): Deployments with hardened security contexts, Traefik IngressRoute or a standard Ingress, cert-manager Certificate, a CloudNativePG `Cluster` (or an external database via a Secret), PDBs, optional HPA/NetworkPolicies, `values.schema.json`, a `helm test`. Migrations run as an init container of the API pods (`db/migrate.ts` waits for the database and holds an advisory lock).
- **Standalone / desktop app** (local install, no Authentik, no server): `bun run --cwd packages/backend build:standalone` compiles one executable (API + web app + embedded PGlite; `scripts/build-standalone.ts` generates `.build/entry.ts` that embeds the frontend `dist`, `postgres.wasm/.data` and the migrations). `src/standalone/main.ts` is the entry: `AUTH_MODE=local` (one built-in user; `config.ts` forces `host` 127.0.0.1 and refuses a non-loopback `HOST`), the backend serves the SPA itself (`spaHandler`, `createApp({ spa })`; `/env-config.js` sets `VITE_AUTH_MODE=local`, which `main.ts` of the frontend treats like fake), a lock file `argent.lock` stops a second process opening the same database, SIGTERM/`shutdown` line/stdin close flush PGlite via `closeDb()`. Files: config `~/.config/argent/config.json` (`$XDG_CONFIG_HOME`, Windows `%APPDATA%\Argent`; keys `port` default 47821, `dataDir`, `backupDir`, `databaseUrl`, `coingeckoApiKey`, `openBrowser`; `lib/settings.ts`), data `~/.local/share/argent` (XDG), macOS `~/Library/Application Support/Argent`, Windows `%LOCALAPPDATA%\Argent`, DB in `<data>/db` (`lib/appPaths.ts`); precedence flags > env (`ARGENT_PORT`, `ARGENT_DATA_DIR`, `ARGENT_CONFIG_DIR`, `DATABASE_URL`) > file > defaults; generic `PORT` is deliberately ignored. In the compiled binary PGlite gets its wasm via `db/pgliteAssets.ts`; with `databaseUrl` migrations run on start (`ARGENT_MIGRATE_ON_START`). `packages/desktop` is a Tauri 2 shell: the executable is its sidecar (`bun run --cwd packages/desktop bundle`), the Rust side (`src-tauri/src/main.rs`) builds the window itself (only the builder has `on_download`; without a handler wry never gives WebKitGTK a destination and `a.download` clicks save nothing; finished downloads dispatch an `argent-download` event the Backup tab shows) and waits for the `ARGENT_LISTENING <url>` line, navigates the window there and sends `shutdown` on exit. Backups in the desktop app: no download manager there, so `createApp({ local })` mounts `/api/local/*` (`routes/localRoutes.ts`, `services/localSettings.ts`): `GET/PUT /settings` (the backup folder, validated, created, kept in `config.json`) and `POST /backup` (writes a new `argent-backup-<date>-<hhmm>.json` there); the Backup tab shows `LocalBackupFolder` (a **Browse…** button opens the native folder dialog: Rust command `pick_folder` with `tauri-plugin-dialog`; the page comes from `http://127.0.0.1:<port>`, a *remote* origin for Tauri, so `build.rs` declares the command in the app manifest and `capabilities/local-server.json` grants `allow-pick-folder` to that origin; the frontend calls `window.__TAURI_INTERNALS__.invoke` via `lib/desktop.ts`, button only when `isDesktopApp()`) instead of the download button when `isLocalMode()`. **App password** (standalone only): `services/localLock.ts` (`createLocalLock`; scrypt hash kept as `passwordHash` in `config.json` via `updateSettingsFile`, sessions are random tokens in memory only so a restart locks it, 5 wrong guesses → 30 s block) and `routes/lockRoutes.ts` (`/api/local/auth/status|unlock|lock`, `PUT /password`, `POST /password/remove`; the session cookie `argent_session` is HttpOnly + SameSite=Strict). `createApp({ lock })` puts a guard in front of every `/api` route except those (401 `{ error, locked: true }`). It does not encrypt the files on disk. Frontend: `App.vue` shows `features/lock/UnlockScreen.vue` instead of everything while `useLockStatus()` says locked (the client dispatches `LOCKED_EVENT` on a 401 with `locked`), the Profile page shows `features/lock/PasswordCard` (local mode only) to set/change/remove it, and the top-right menu has **Lock** instead of Sign out in local mode (`useLockApp`, which `forgetAll()`s the query cache; disabled until a password is set). `scripts/smoke-standalone.sh` checks the binary.
- CI: `.github/workflows/ci.yml` has five jobs: `standalone` (build + smoke the executable) and `desktop` (Tauri build on Ubuntu) besides the three below: `check` (`bun run check` + frontend build), `chart` (`bun run check:chart` + kubeconform against the Kubernetes/CRD schemas) and `images` (build both images, `scripts/smoke-images.sh`, Trivy scan).

## Commands
- `bun install && bun run db:generate`, then `bun run dev:backend` and `bun run dev:frontend`. No external services are needed locally.
- `bun run db:generate`: generate a migration from `schema.ts` changes.
- `bun run db:migrate`: apply migrations.
- `bun run --cwd packages/backend db:check`: exits 1 if `schema.ts` has drifted from the committed migrations. Run before pushing schema changes.
- **`bun run check`**: the one command to run before finishing work. Type-checks all three packages (test files included), runs every test, and verifies migrations match `schema.ts`.
- `bun run typecheck` / `bun run test`: the two halves separately. Per package: `bun run --cwd packages/<name> test|typecheck`.
- `bun run build`: build all packages.
- `bun run check:chart`: lints and renders the Helm chart with every `charts/argent/ci/*-values.yaml` and asserts hardening, wiring and required settings (needs `helm`). `scripts/smoke-images.sh` runs the two images hardened like Kubernetes runs them (`CONTAINER_CLI=podman` works).

## Local dev mode
- The `.env.development` files are not committed: copy `packages/backend/.env.example` and `packages/frontend/.env.example` (they document every dev setting).
- Backend `.env.development`: `AUTH_MODE=fake` injects a static dev user. **With `DATABASE_URL` unset it uses an embedded PGlite database that persists in `packages/backend/.data/pglite`** (gitignored): what you enter survives restarts and `bun --hot` reloads, and pending migrations are applied on start. `bun run db:reset` throws it away; `PGLITE_DATA_DIR` moves it; `DATABASE_URL=memory` gives a throw-away in-memory database (the tests force this); a postgres URL uses that server. Where it lives is decided by `resolveDbLocation` (`db/location.ts`); production requires a real `DATABASE_URL` (`config.ts`).
- Frontend `.env.development`: `VITE_AUTH_MODE=fake` uses `createFakeAuth()`, which is the same `Auth` object the real OIDC flow produces, so `useAuth()` works unchanged.
- PGlite is a devDependency and is not in the production image. **PGlite 0.6 runs Postgres 19, and a data directory written by another Postgres major (0.2 was 16) cannot be opened**: `db/pgliteVersion.ts` checks `PG_VERSION` at startup and tells the user to back up with the old version and restore into a fresh directory (a test compares `PGLITE_POSTGRES_MAJOR` with what the installed PGlite really creates, so the next PGlite upgrade is flagged). PGlite 0.6 takes `pgliteWasmModule`/`initdbWasmModule`/`fsBundle` (the standalone build embeds `pglite.wasm`, `initdb.wasm`, `pglite.data`) and keeps a process alive for a while after its last query: scripts that open it should `process.exit()` (data is on disk already).

## Database / migrations (important)
- Drizzle migrations in `packages/backend/drizzle/` (currently 0000–0029) are tracked in git. Never gitignore them.
- Run `db:generate` BEFORE editing `schema.ts`, or restart the backend after generating. Bun `--hot` re-evaluates `db/index.ts` on source changes; it reuses the already open PGlite client (kept on `globalThis`) so data is not lost and the directory is never opened twice, and it applies new migrations — but a `schema.ts` edit without a generated migration leaves the dev database on the old schema.
- Always create migrations with `db:generate` (0018 was generated this way). Don't hand-write them without also updating `drizzle/meta/` snapshots and the journal. Drift makes `db:generate` hang on an interactive rename prompt. Check with `db:check`.

## Backend layout (`packages/backend/src`)
- `app.ts`: `createApp({ auth?, logRequests? })` builds the Hono app (all routes under `/api`: `me`, `accounts`, `categories`, `transactions`, `import`, `subscriptions`, `admin`, `crypto`, `metals`, `stocks`, `mortgages`, `loans`) plus the JSON `onError`/`notFound` handlers. `index.ts` only starts the server and the background jobs. Tests use `createApp` directly.
- `middleware/validate.ts`: `validateJson(schema)` validates the body against a schema from `@argent/shared` and answers `400 { error, issues }`; handlers then read `c.req.valid("json")`. **Every route that reads a JSON body must use it** (schemas live in `packages/shared/src/schemas.ts`; the `*Body` types in `types.ts` are derived from them with `z.input`).
- `services/backgroundJobs.ts`: `runBackgroundJobs(trigger)` = link transfers, THEN detect subscriptions, queued sequentially with errors logged. Used after imports, on startup and periodically. Don't fire `linkTransfers()`/`detectSubscriptions()` ad hoc and un-awaited.
- `config.ts`: `loadConfig()` validates the environment once at startup (fake auth refused and group names/CORS required in production); read settings from `config`, not `process.env`.
- `routes/ownerRoutes.ts`: `mountOwnerRoutes(app, { resource, canView })` adds the owner-only `DELETE /:id`, `POST /:id/members` and `DELETE /:id/members/:groupName` to a router; it is mounted by every shared-resource router (crypto, metals, stocks, mortgages, loans, properties, equity). Don't write those handlers again: a new shared resource needs a definition in `services/sharedResources.ts` and one `mountOwnerRoutes` call. Non-viewers get 404, viewers/editors 403.
- `middleware/guards.ts`: `requireAdmin` (admin router) and `isOwnerOrAdmin(resource, user)` (owner-only actions on shared resources) — don't write these checks inline.
- `middleware/auth.ts`: JWT middleware, plus `syncProfileOnce` (Map keyed by sub, iat-based).
- `services/accessControl.ts`: one generic resolver over "owned or shared with a group" resources (accounts, portfolios, mortgages, loans). Use `toAccessContext(user)` to build the context, `canView*`/`canEdit*` for single-resource checks, and `getViewable*Ids`/`getEditable*Ids` for lists. Add new shared resource types by defining a `SharedResource` there.
- `services/camt053.ts`: CAMT.053 parser. Dedup uses a SHA-256 `import_hash` (globally unique) from `computeImportHash`: account IBAN, debit/credit direction, amount (normalised to 2 decimals), currency, date, counterpartyIban, reference, description. Migration 0019 recomputes stored hashes in SQL from the same columns; `routes/importHash.test.ts` checks the SQL and the TS agree, so change both together. Identical entries on the *same* account still collapse (inherent to a content hash).
- `services/transferLinker.ts`: links internal transfers by shared EndToEndId or by counterpartyIban matching an own account. Never links two legs on the same account.
- `services/subscriptionDetector.ts`: detects recurring DBIT patterns, grouped by `(accountId, counterpartyIban)`. Gaps must be within ±20% of the median (floor ±5 days) and amounts within ±5%. New ones are created as `candidate`. Existing `candidate`/`confirmed` rows only get their stats updated, and `dismissed` pairs are skipped. Manual `POST /subscriptions` creates `confirmed` and retroactively links transactions; for a pair that already has a `candidate` (or a `dismissed` tombstone) it confirms that record instead (200, no duplicate, name kept unless one is given); only an already `confirmed` one is a 409. Dismiss unlinks transactions and leaves a `dismissed` tombstone. Links are write-time via `transactions.subscriptionId`. Each detection pass first unlinks transactions that became transfers and removes `candidate`s left empty (confirmed ones are kept).
- `lib/dates.ts`: all backend date arithmetic (`addDays`, `daysBetween`, `addMonths`, `completedMonths`, `todayIso`) on `YYYY-MM-DD` strings, independent of the server's time zone; "today" is the UTC date. **Never use local `Date` getters/`setDate` for calendar dates** (a local `Date` made "+2 days" one day early across daylight-saving changes in Europe/Amsterdam). `bun run test:tz` (part of `bun run check`) runs the date-sensitive tests under five zones; in tests build instants with `Date.UTC(…, 12)`, not `new Date(y, m, d)`.
- `services/fifo.ts`: `computeFifo(trades, symbol, baseCurrency)` returns `{ balance, avgCostBasis, totalCost, realizedPnL }`. Shared by crypto and stocks.
- `services/money.ts`: exact decimal arithmetic (`Decimal` from decimal.js, `cents()` rounds half up in decimal, `isOpenQuantity`/`DUST_QUANTITY`, `exceedsBalance`). **Amounts that are summed, split or rounded go through `Decimal`, never `n * 100 / 100` or float `+=`** (a thousand buys of 0.10 used to drift; 1.005 rounded to 1.00). `computeFifo` is exact (lot costs kept as totals, taken in proportion) and returns money in whole cents; unit prices (`avgCostBasis`) are not rounded. Don't write new `1e-8`/`1e-10` epsilons: oversell checks are exact via `exceedsBalance`.
- `services/positions.ts`: `buildPositions` / `summarizePositions` build the positions and totals for crypto and stocks (value known only when every open position has a price); the routes only fetch data and prices.
- `services/priceService.ts`: CoinGecko (crypto: ~35 pinned tickers; any other ticker is resolved by CoinGecko search, best market-cap rank wins, cached; prices at full precision in one batched call via `getCryptoPrices`), Yahoo front-month futures `GC=F`/`SI=F`/`PL=F`/`PA=F` (USD/troy oz) + Frankfurter (metals; metals.live, used before, no longer exists), Yahoo Finance + Frankfurter (stocks/ETFs; quotes in a minor unit such as London's pence `GBp` are converted via `MINOR_UNITS`). 5-min in-process cache. `getCryptoHistory`/`getStockHistory` (CoinGecko `market_chart`, Yahoo chart ranges; downsampled, 15-min cache) feed `GET /crypto|stocks/history/:symbol?range=1m|3m|6m|1y|max&currency=EUR|USD` (validated with `validateQuery(historyQuerySchema)`; empty `points` when unknown). Stock history converts at today's FX rate. CoinGecko's key-less API is heavily rate limited: `coingecko()` honours 429/`retry-after` (no calls while blocked), crypto prices and history fall back to Yahoo's `SYM-EUR`/`SYM-USD` pairs, stale prices (<24 h) and history (<7 d) are served while a provider is down, identical in-flight history requests are shared, and `PriceProviderError` (→ HTTP 503 on the history route) separates "try later" from "unknown symbol". An optional `COINGECKO_API_KEY` (free demo key) raises the limit.
- `services/amortization.ts`: `computePartState(part, payments, asOf)` simulates month by month for linear/annuity/interest_only parts with extra payments. Shared by mortgages and loans. A part's `rateType` is `nominal` (monthly rate = rate/12, the default) or `effective` (monthly = (1+rate)^(1/12)-1); banks often quote the effective rate. Payment m is due m months after `startDate` on the same day of the month (day-aware: `monthsElapsed` counts payments whose date has passed). Without a `firstPaymentDate` there is no stub period, so set the start date one month before the first installment. With a `firstPaymentDate` (payout mid-month, installments on the 1st) the start date is the payout date and the interest of the partial month is added to the balance (annuity/linear; spread over the term, as banks do) — a 250,000 payout on 9 Oct with the first installment on 1 Dec gives 1076.43 instead of 1074.34; the term then counts from the first payment. **Fixed-rate periods**: a part's own rate is its first rate; `*_part_rates` (`POST /:id/parts/:pid/rates`, `DELETE …/rates/:rateId`, one change per date, inside the part's term) hold the later ones (the end of a fixed-rate period). The rate of a period is the latest change on/before the day the period starts (a change inside a period applies from the next). At a change an annuity's installment is recalculated from the balance, the new rate and the months left in the **contract** (extra payments do not shorten that), linear keeps its principal portion, interest-only pays the new interest. A change dated in the future is an assumption: the state is projected with it (`currentRate`, `nextRateChange`); `getLiabilities` (net worth) passes the rates too. `resetRecalculation` (`contract` default | `remaining`) is a per-part option: `remaining` spreads the new annuity installment over the term left at the current payment (shortened by extra payments), as some banks do. **Closing a part** (`POST …/parts/:pid/close` `{ closedOn, continuation: [new parts] }`, `DELETE` reopens, `GET …/carry-over?date=` gives the balance on a day): `closedOn` makes the part owe nothing from that day (`computePartState` returns zeros and `carriedOver`, the balance on the closing day); the new parts start that day with `continuesPartId` set (no FK: restore inserts in any order), must add up to at most the carried-over balance (the rest counts as repaid), and are created in one transaction. A part whose next rate change is within 3 months is highlighted yellow in the UI (`rateChangeSoon`). A part can be created with its `rates` in the same request (also the preview). `POST /mortgages|loans/preview-part` (`previewDebtPartSchema`, no name needed) returns the same state for a part that is still being entered, saving nothing; the add-part form shows it as a debounced preview (`PartPreview`, `useDebtPartPreview`, `useDebounced`) so the numbers can be checked against the bank's before saving. Extra payments take effect on their own date (the interest of that period drops in proportion to the days left) and, with the default effect `shorten_term`, the payment size stays, so they shorten the term; with `lower_payment` (a per-extra-payment choice, not for interest-only) the remaining balance is instead spread over the contract months left, from the next installment on (an annuity's installment or a linear part's principal portion goes down, the end date stays): `monthsRemaining`/`projectedEndDate` are the projection, `totalMonths` is the schedule.

## Testing (`bun test`)
- Backend tests live next to the code (`*.test.ts`) and run on in-memory PGlite. `test/setup.ts` (a `bunfig.toml` preload) forces `DATABASE_URL=memory` and installs `test/fakeFetch.ts`, so **no test can touch a real database or the network**.
- All test files in a run share one database (one process), so tests create their own uniquely-named data and assert only on it, never on global counts. `test/helpers.ts` has `api/get/post/...` (real app as the fake admin), `clientAs(user(...))` (real app as any user/role), `camt(...)` (CAMT.053 builder), `upload(...)` (waits for background jobs to settle).
- `bun run check` also runs the shared (`schemas.test.ts`) and all frontend tests.
- Modules with in-process caches (priceService) are loaded fresh per test with `import("./x.ts?fresh=N")`.
- Backup/restore replaces ALL data, which is fine inside the suite because the round trip restores what it backed up. Backup, restore, the restore counts and the restore request schema are all derived from `BACKUP_ORDER` in `services/backup.ts` (tables in insert order, parents first). **A new table = one new key there** — `backup.test.ts` fails if a table in `schema.ts` is missing or mis-ordered. The admin sharing overview is likewise driven by `SHARING_OVERVIEW` in `services/sharedResources.ts`, which also holds the shared-resource definitions used by access control.

## Domain models
- **Crypto and stocks**: immutable trade ledger plus FIFO. `stock_trades` has the same shape as `crypto_trades`. The stocks API takes `{type: "buy"|"sell", symbol, quantity, amount}` and translates it to from/to. Crypto also supports swaps, with `baseCurrencyAmount` auto-computed by FIFO cost-transfer. Stock dividends (`stock_dividends`) sit outside the FIFO chain and are deletable.
- **Cash account of crypto/stocks portfolios** (`portfolios.account_number/opening_cash/opening_cash_date`, `portfolio_cash_movements`): the money is deposited in the broker/exchange account before it is exchanged. Movements are deposit/withdrawal/fee/interest (editable, deletable: `routes/cashRoutes.ts`); the **cash balance is derived** (`services/cash.ts#computeCash`): opening cash + movements − buys + sells (+ dividends for stocks), only counting what is dated on/after `openingCashDate` (like account balances). Swaps never touch it; it may go negative (history can be incomplete, so it is shown, not refused). `GET /crypto|stocks/:id` returns `cash` and `cashMovements`; it counts in the dashboard net worth (`Holding.cash`) and in the overview tab per currency. Metals have no cash account. Not built: suggesting deposits from bank transactions whose counterparty IBAN is the portfolio's account number (TODO).
- **Metals**: per-lot physical inventory with no FIFO. `metal_lots` plus immutable `metal_sales`.
- **Property** (`properties`, `property_valuations`, `property_members`, `property_mortgages`, `property_loans`): anything with a value but no ledger (house, apartment, land, vehicle, business, other). Value = dated, **manually entered valuations**; the latest one dated today or earlier counts, flat until the next (`services/property.ts#currentValueOf`; else the purchase price; else unknown). A property can be linked to mortgages/loans (FK link tables, cascade both ways) so `debt` = their current balances (`getLiabilities`, only ones the user can view) and `equity` = value − debt. `GET /properties` is the read model (no GET /:id); `PUT /:id/links` only touches links to liabilities the user can see. Net worth counts the property as an asset and the linked mortgage stays a liability.
- **Equity compensation / stock options** (`equity_plans`, `equity_grants`, `equity_prices`, `equity_plan_members`): one plan per company holding its grants. A grant vests either **over time** (`vestStart`, `cliffMonths`, `vestMonths`; monthly after the cliff, day-aware, `services/equity.ts#vestedOptions`) or **on exit** only; a plan that is partly both is two grants. Share prices are manual and dated (latest dated today or earlier counts, flat until the next). Value per option = max(0, price − strike). **Only the vested value of time-vested grants counts in net worth**; still-vesting and on-exit value are shown but not counted. All values are pre-tax. `GET /equity` is the read model.
- **Pensions** (`pension_plans`, `pension_statements`, `pension_transfers`, `pension_plan_members`; `routes/pensions.ts`, `services/pension.ts`): one plan per arrangement, `kind` = `state` | `occupational_db` (rights: yearly income, no capital) | `occupational_dc` (a pot) | `personal`; generic on purpose (the Dutch system: AOW, pension fund, lijfrente/banksparen; also fits a 401(k) or a UK scheme). A plan is **active**, **frozen** (no new accrual, the stored `status`) or **closed** (`closedOn` today or earlier; derived `state`), so the Dutch Wtp switch, a job change or keeping the old scheme are all "close/freeze + open another": the kind of a plan never changes. What it is worth comes from dated, manually entered **statements** (no provider has an export): `capital`, `accruedIncome` (yearly, payable from retirement), `projectedLow/Expected/High` (the new system's three scenarios; the old one fills only expected), `partnerIncome`, `inTodaysMoney` (real vs nominal); at least one figure, scenarios in order. The latest statement dated today or earlier counts, flat until the next (`latestStatementOf`). `expectedIncome` = expected scenario, else accrued. **Net worth**: only `netWorthValue` = the capital of a plan that is not closed and has `countInNetWorth` (default true for DC/personal, false for rights and state; per-plan switch); rights and the state pension are income, never counted. Everything is pre-tax. **Transfers** (`POST /pensions/transfers`, `DELETE /pensions/transfers/:id`; `kind` `transfer` = waardeoverdracht | `conversion` = rights became a pot; optional `capital` arrived and `incomeGivenUp`; `closeFrom` default true closes the old plan on that date) have no foreign keys (like `continuesPartId`) and need edit rights on both plans; a plan lists the transfers on either side and names the other plan only when the user may see it. Frontend: `features/pension/` (`PensionPage` → `PlanCard`: figures, transfers, `StatementHistory` + `StatementForm`, `PlanControls` (freeze, close, reopen, move, count), `TransferForm`, `PlanActions`), the Dashboard has a Pensions tile and the pots count in net worth. Not built: contributions (a `transfer` type there would keep returns honest), a retirement-income projection against a target.
- **Mortgages and loans**: identical structures (`*_parts`, `*_extra_payments`, `*_members`). One implementation: `routes/debtRoutes.ts` (`debtRoutes(config)`, mounted by `routes/mortgages.ts` and `routes/loans.ts`, which only pass their tables and access checks) and `DebtPage` on the frontend. A change to debts is made once.
- **Accounts**: `type` is checking, savings or cash. `source` is `import` (created by a CAMT.053 import) or `manual` (entered by hand, for banks without an export such as Buut, and for cash): `POST /accounts` (owner = caller; `iban` optional, without one the unique `iban` column holds the placeholder `manual:<uuid>`, which `hasRealIban` from `@argent/shared` detects so the UI never shows it), `DELETE /accounts/:id` only for manual accounts without transactions. Transactions entered by hand (`POST /transactions`, `isManual`, `importHash` = `manual:<uuid>`, currency taken from the account, `amount` positive + `direction` CRDT/DBIT) can be edited (`PUT`) and deleted; imported ones are read-only (409). They link to transfers like any other (suggestions by amount/date, e.g. an ATM withdrawal and the cash it adds); editing amount/direction/date of a linked one unlinks it, deleting leaves the peer unlinked. Frontend: `features/accounts/AddAccountForm`, `features/transactions/ManualTransactionForm`, the Cash page. `balance` is computed as `openingBalance` plus the sum of transactions since `openingBalanceDate`.
- Portfolios: `portfolios(type: crypto|metals|stocks, currency: EUR|USD, broker)`. `broker` is stocks-only.

## RBAC
- Global, from the JWT `groups` claim: `AUTHENTIK_ADMIN_GROUP` is admin and `AUTHENTIK_IMPORT_GROUP` can import (admins can too). The code defaults are `argent-admin` / `argent-import`, but `.env.development` sets `finance-admin`. Always set both explicitly.
- Per-resource roles (accounts, portfolios, mortgages, loans) live in `*_members(…, groupName, role)` with role `viewer` or `editor`. The owner (or an admin) manages members and deletion.
- No user table. Users and groups live in Authentik. `user_profiles` only caches email, name and theme.
- Importing a new IBAN creates the account with no access, and an admin assigns groups later. Importing an existing IBAN requires editor access, otherwise 403.

## Frontend layout (`packages/frontend/src`)
Vue 3 (`<script setup lang="ts">` SFCs). Pages are thin: they pick a feature and pass configuration. Real UI lives in `features/<area>/` and shared pieces in `components/`.
- `api/`: the only place that talks HTTP. `client.ts` (`http.get/post/...`, `ApiError`, token getter set by the auth object), one module per domain (`accounts`, `transactions`, `admin`, …), **generic factories** `portfolioApis` (crypto/metals/stocks) and `debtApis` (mortgages/loans), `keys.ts` (every query key) and `queries.ts` (`use*` composables + `useInvalidate`). **Never write `useQuery({ queryKey: [...] })` or `invalidateQueries({ queryKey: [...] })` in a page/component** — add a composable/key in `api/` so a resource has one key and refreshes everywhere. Keys are hierarchical (everything transaction-related is under `["transactions"]`). Query composables return refs: use `.value` in script, destructure the top-level refs for templates; reactive params are `MaybeRefOrGetter`.
- `auth/`: `createOidcAuth(settings)` / `createFakeAuth()` build a reactive `Auth` object (`user`, `isLoading`, `error`, `isAuthenticated`, `ready`, `signinRedirect/Callback`, `signoutRedirect`) and point the API token getter at it; `authPlugin(auth)` provides it, `useAuth()` injects it. `config.ts` reads OIDC config from `window.__ENV__`.
- `router.ts`: `createAppRouter(history, auth)` with lazy routes; the `beforeEach` guard awaits `auth.ready` and starts the sign-in when there is no session (`/auth/callback` is `meta.public`). `/transactions` redirects to `/overview`. `App.vue` is the loading/error gate plus `Layout` around `<RouterView>`.
- `components/ui/`: primitives — `Button` (type="button" by default), `Input`/`Select` (`density`, `v-model`; `Input` keeps the raw string even for type=number), `Card` (the white bordered panel; `size="xl"`, `as="form"`; don't spell the classes out), `Field` (provide/inject associates label↔control, shows `error`), `FieldGroup`, `SegmentedControl`, `ConfirmButton` (inline confirm; never use `window.confirm/alert`), `RoleBadge`, `Th`/`Td` (table cells: `align`, `dense`, `mono`, `tone`; don't spell out `px-4 py-3 …`), `LoadingText/ErrorText/EmptyState`, `vFocus` (autofocus directive). `components/SharingPanel.vue`, `Pagination.vue`, `Icon.vue` (named inline SVGs), `Layout.vue` are shared widgets.
- `features/portfolios/PortfolioPage.vue`: with >1 portfolio and an `#overview` slot it adds an **Overview** tab (first and default) fed with every visible portfolio's detail; `overview.ts` holds the pure aggregation (per currency — EUR/USD are never summed — then per symbol, or per metal) and `AssetsOverview`/`MetalsOverview` render it. Clicking a symbol in any positions table opens `AssetChart` (price history + the portfolio's buys/sells as ▲/▼ markers) built on `components/charts/LineChart.vue` (plain SVG, hover/keyboard tooltip, table view).
- `features/equity/` (`EquityPage` → `PlanCard`: share price, vested / still vesting / on exit, `GrantsTable` with vesting progress, `GrantForm` (add + edit), `PriceHistory` step chart + `PriceForm`). Forms use `novalidate`.
- `features/property/` (`PropertyPage` → `PropertyCard`: worth/owed/equity/gain, linked liabilities, `ValuationHistory` step chart + table, forms). Forms there use `novalidate` so the shared zod schemas explain errors instead of the browser's number checks.
- `features/debts/` (`DebtPage` serves both Mortgages and Loans via `DEBT_KINDS`), `features/portfolios/` (`PortfolioPage` shell with a scoped slot `{ portfolio }` + `crypto/`, `stocks/`, `metals/` views), `features/transactions/`, `features/subscriptions/`, `features/dashboard/` (`summarize.ts` is the pure net-worth logic), `features/pension/`, `features/admin/`, `features/settings/`, `features/import/`, `features/accounts/`, `features/lock/`. **One Settings page** (`pages/Settings.vue`, tabs via `?tab=`): Accounts, Labels, Import (importers), Access + Sharing (server admins only; hidden in the standalone app, which has no groups) and Backup & Restore (admins); the old Admin page is gone (`/admin` redirects to `?tab=access`). Profile (top-right menu) holds identity, theme and, in the standalone app, the password.
- Forms validate with the **same zod schemas the backend uses**: build the request body, `check(schema, body)` from `useFormErrors()` (`lib/validate.ts`; `errors` is a ref), show `errors.<field>` via `<Field :error="…">`, and only then `mutate()`.
- `lib/format.ts`: all number/currency/date/percentage/P&L formatting (`fmtPct`, `fmtPrice`, …). Don't define `fmt*` helpers inside components.
- Tailwind 4: the Vite plugin `@tailwindcss/vite` and CSS-first config in `src/index.css` (`@import "tailwindcss"`, a `dark` variant on the `.dark` class, and base rules that keep the Tailwind 3 defaults: gray-200 borders, pointer cursor on buttons, gray-400 placeholders); sources are detected automatically. Use the v4 names (`rounded-sm` is the old `rounded`, `rounded-xs` the old `rounded-sm`, `shadow-sm`/`shadow-xs` likewise, `outline-hidden`, `shrink-0`, `px-3!` for important). `vue-tsc` is the type checker, which needs TypeScript 5.x and runs only in `typecheck`/`check` (`bun run build` is a plain `vite build`, which strips types without checking them): the frontend stays on 5.9 while the root, shared and backend use TypeScript 7 (`noUnusedLocals` on); test files are checked separately (`tsconfig.test.json`).

## Frontend testing (`bun run test` in `packages/frontend` = Vitest)
- Vitest + happy-dom + Testing Library for Vue (`test/setup.ts`). Use `bunx vitest run`, not `bun test` (that is Bun's own runner).
- `await renderApp(Component, { props, slots, route, routes, auth, client, router })` from `test/render.ts` wraps vue-query, a memory router (with a catch-all blank route; pass `routes` to assert navigation via `router.currentRoute.value`), and fake auth. It is async because the router must finish its first navigation. `renderTemplate` renders a template string; `runComposable` runs a composable in an app context. Pass component events as `onFoo` props.
- The API is faked at the `fetch` level: `mockApi({ "GET /x": data, "POST /x/:id": ({ body, params }) => … })` (`test/fakeApi.ts`); assert with `api.calls("POST", "/x")` and `api.unmatched` (requests nobody mocked). Because tests go through the real network layer, they survive refactors of `src/api/`.
- `test/fixtures.ts` has fixtures typed against `@argent/shared`; find controls with `screen.getByLabelText`.
- The token getter in `api/client.ts` is module-level state (set when an auth object is created): tests that set it must reset it.
- Run in random order (`bunx vitest run --sequence.shuffle`) when touching shared test state.

## Env vars
- Backend: `DATABASE_URL`, `AUTHENTIK_ISSUER`, `CORS_ORIGIN`, `AUTHENTIK_ADMIN_GROUP`, `AUTHENTIK_IMPORT_GROUP`, optional `COINGECKO_API_KEY`.
- Frontend: `VITE_AUTHENTIK_AUTHORITY`, `VITE_AUTHENTIK_CLIENT_ID`, `VITE_AUTH_MODE=fake` (dev only).

## Deployment (Helm chart `charts/argent`)
- Install: see `charts/argent/README.md`. `host`, `auth.issuer` and `auth.clientId` are required (the chart refuses to render without them). The CloudNativePG operator, cert-manager (+ a `letsencrypt` ClusterIssuer) and an ingress controller must exist; create the Authentik OIDC app as a public client with redirect URI `https://<host>/auth/callback`.
- The API gets `DATABASE_URL` from the CloudNativePG-generated Secret `<release>-postgres-app` (key `uri`), so no database password lives in values; `database.mode=external` reads it from a Secret you provide. The cluster is kept on `helm uninstall` (`helm.sh/resource-policy: keep`).
- The SPA's runtime settings are written by `docker/frontend-entrypoint.sh` to `/tmp/env-config.js` (served as `/env-config.js`) from `VITE_AUTHENTIK_*`, so the root file system stays read-only. The frontend listens on 8080 (`/healthz`), the API on 3000 (`/health`).
- Images: the Bun binary is copied from the official `oven/bun` image (version `BUN_VERSION`, same as CI); nginx comes from the SLE BCI repository (1.21.x with SUSE's security patches) installed into a copy of the micro root. Swapping the base for another hardened source (Chainguard, Docker Hardened Images) only touches the Dockerfiles.
- Open: replace the `your-registry/argent-*` image defaults, push images from CI, run the chart on a real cluster (it is only lint/render/schema-checked and the images smoke-tested), and try the real Authentik login.
